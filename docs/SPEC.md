## 1. ภาพรวม
เว็บแบ่งเป็น 5 ส่วน (ใช้ซ้ำได้ทุกปี ดูหัวข้อ 12 รอบการจัดงาน) โดยหน้าเว็บอยู่บน GitHub Pages (static hosting) งานที่ต้องจำ ตรวจ หรือเก็บข้อมูล (เช็กรหัสนักศึกษาซ้ำ เก็บไฟล์ admin login) ฝากไว้กับ **Supabase**

| ส่วน | ผู้ใช้ | ทำอะไรได้ |
|---|---|---|
| หน้าหลัก | ทุกคน | อ่านรายละเอียดโครงการ เปิด PDF คำชี้แจงแบบ pop up กดสมัคร |
| หน้าสมัคร | นักศึกษา | กรอกข้อมูลทีม สมาชิก ที่ปรึกษา ตั้ง PIN แล้วรับใบสรุป |
| ตรวจสอบการสมัคร | ผู้สมัคร | กรอกชื่อทีมอังกฤษ + PIN ดูสถานะ อัปโหลดไฟล์เพิ่ม ติดต่อกรรมการ |
| ภาพกิจกรรม | ทุกคน | ดูภาพบรรยากาศงานของแต่ละปี |
| Admin | ผู้จัดงาน | แก้เนื้อหา สร้างปีใหม่ ตั้งช่วงรับสมัคร ตรวจ/อนุมัติทีม เปิดช่องอัปโหลด จัดการภาพ สำรอง/รีเซ็ตข้อมูล |

**กติกาหลักที่ระบบต้องบังคับ:** นักศึกษา 1 คนสมัครได้ 1 ทีม (รหัสนักศึกษาซ้ำ = กด Submit ไม่ได้) · สมาชิกไม่เกิน 7 คนต่อทีม (ตั้งต่อรอบได้) · ที่ปรึกษาไม่จำกัดจำนวน

## 2. สถาปัตยกรรม
GitHub Pages (HTML/JS static: หน้าหลัก+สมัคร, ตรวจสอบ, Admin) → เรียก Supabase ผ่าน RPC/API
Supabase = Postgres + RLS (เข้าถึงผ่านฟังก์ชัน RPC เท่านั้น) · Storage แบบ private · Auth (admin ล็อกอิน) · Edge Function `request-upload` และ `admin-purge`

## 3. แผนผังเว็บ (hash routing — GitHub Pages ไม่รองรับ path ซ้อน)
| หน้า | URL | เข้าได้จาก | ต้อง login |
|---|---|---|---|
| หน้าหลัก | `#/` | ลิงก์เว็บไซต์ | ไม่ |
| ภาพกิจกรรม | `#/gallery` | เมนูบน, แถบภาพบนหน้าหลัก | ไม่ |
| หน้าสมัคร | `#/apply` | ปุ่ม "สมัคร" | ไม่ |
| ตรวจสอบการสมัคร | `#/status` | เมนูบน, ลิงก์จากใบสรุป | ไม่ (ชื่อทีมอังกฤษ + PIN) |
| Admin | `#/admin` | พิมพ์ URL / ลิงก์เล็กท้ายหน้า | ใช่ (อีเมล+รหัสผ่าน) |

Pop up (ไม่ใช่หน้าแยก): คำชี้แจงโครงการ (PDF) บนหน้าหลัก, ใบสรุปการสมัครบนหน้าสมัคร

## 4. หน้าหลัก (7 บล็อก อ่านจาก `public_site()` = `site_settings` + ข้อมูลรอบปัจจุบัน — แก้จาก admin ได้โดยไม่ต้อง deploy ใหม่)
| # | บล็อก | แสดงอะไร | admin แก้ได้ |
|---|---|---|---|
| 1 | Hero | โลโก้และชื่องานกึ่งกลาง บนภาพพื้นหลัง | อัปโหลดโลโก้/ภาพพื้นหลัง แก้ชื่องาน |
| 2 | รายละเอียดโครงการคร่าวๆ | ย่อหน้าสั้นๆ | แก้ข้อความ |
| 3 | ปุ่มรายละเอียดโครงการ | เปิด pop up แสดงคำชี้แจงและรายละเอียดการประกวดเป็น PDF | อัปโหลด PDF ใหม่, แก้ชื่อปุ่ม |
| 4 | ปุ่มสมัคร | ไป `#/apply` + บรรทัดสถานะ (เปิดรับสมัครถึง … / ปิดรับสมัครแล้ว) | แก้ชื่อปุ่ม; สถานะมาจากช่วงเวลาของรอบ |
| 5 | กำหนดการสำคัญ | การ์ดวันสำคัญ (`editions.key_dates`) | แก้รายการ/วันที่ต่อรอบ |
| 6 | ภาพกิจกรรมล่าสุด | 4 ภาพล่าสุดจากอัลบั้มที่เผยแพร่ + ลิงก์ไป `#/gallery` (ซ่อนถ้ายังไม่มี) | แท็บภาพกิจกรรม |
| 7 | Footer | ช่องทางติดต่อ หน่วยงาน ลิงก์ | แก้ข้อความ |

- Pop up PDF: `<iframe>` + ปุ่มปิด + ปุ่มดาวน์โหลด + **ปุ่มเปิดในแท็บใหม่** (มือถือบางรุ่นแสดง PDF ใน iframe ไม่ได้). ไฟล์ใน Storage bucket `public-assets` (public-read)
- ปิดรับสมัคร (ยังไม่ถึงวันเปิด, เลยเวลาปิด หรือ admin ปิดบังคับ): ปุ่มสมัครเป็นสีเทา + ข้อความปิดรับสมัคร

## 5. หน้าสมัคร
ฟอร์มหน้าเดียว → Submit → pop up ใบสรุปให้ยืนยัน → Confirm จึงบันทึกจริงและดาวน์โหลดภาพใบสรุปทันที

| กลุ่ม | ช่อง | กฎการตรวจ |
|---|---|---|
| ทีม | ชื่อทีม (ไทย) | บังคับกรอก |
| ทีม | ชื่อทีม (อังกฤษ) | บังคับ · **ไม่ซ้ำกับทีมอื่น** (ไม่แยกตัวพิมพ์เล็ก-ใหญ่ ยุบช่องว่าง) เพราะเป็นคีย์ค้นหา |
| สมาชิก (1–7) | รหัสนักศึกษา | ตัวเลข 13 หลักพอดี · **ไม่ซ้ำทั้งในทีมและข้ามทีม (ภายในรอบการจัดเดียวกัน)** |
| สมาชิก | ชื่อ-สกุล | บังคับ |
| สมาชิก | เบอร์โทร | ตัวเลข 10 หลัก ขึ้นต้น 0 |
| อาจารย์ที่ปรึกษา (ไม่จำกัด, ≥1) | ชื่อ-สกุล · สาขา · คณะ | บังคับทุกช่อง |
| ความปลอดภัย | PIN 4 หลัก (+ ยืนยัน PIN) | ตัวเลข 4 ตัว ใช้ตรวจสถานะ ส่งเอกสาร ติดต่อกรรมการ |
| ยืนยัน | ช่องรับทราบ | ต้องติ๊ก · ข้อความ admin แก้ได้ |
| ยืนยัน | PDPA | ต้องติ๊ก · ข้อความยินยอมใช้ข้อมูลส่วนบุคคล |
| ปุ่ม | Submit | กดได้เมื่อทุกช่องผ่านและไม่มีรหัสซ้ำ · ชื่อปุ่ม admin แก้ได้ |

### ตรวจรหัสนักศึกษาซ้ำ 2 ชั้น
1. **หน้าเว็บ (ช่วยผู้ใช้):** ครบ 13 หลักแล้วเรียก `student_id_taken` (คืนแค่ซ้ำ/ไม่ซ้ำ) → แถบแดงที่ช่องนั้น + ล็อก Submit
2. **ฐานข้อมูล (ตัวตัดสิน):** unique index `members_student_id_key` + `submit_team` ทำงานใน transaction เดียว — สองคนกด Confirm พร้อมกันด้วยรหัสเดียวกัน ผ่านแค่ทีมเดียว

ข้อความแจ้งเตือนไม่บอกว่ารหัสอยู่ทีมไหน/ใครสมัคร: "รหัสนี้สมัครแล้ว หากคิดว่าผิดพลาดติดต่อฝ่ายจัดงาน"

### ลำดับ Submit → ใบสรุป
1. กด Submit → ตรวจครบทุกช่องอีกครั้ง (ยังไม่บันทึก)
2. pop up ใบสรุป (ปุ่ม "แก้ไข" / "Confirm")
3. Confirm → `submit_team` บันทึกทีม สมาชิก ที่ปรึกษา ความยินยอม ในครั้งเดียว สถานะ = "รอ admin ตรวจสอบ"
4. สำเร็จ → สร้างภาพ PNG ฝั่งผู้ใช้ และ**ดาวน์โหลดทันที**
5. ล้มเหลว (รหัสซ้ำทันกัน, เน็ตหลุด) → ไม่ดาวน์โหลด ฟอร์มยังอยู่ครบ

**ใบสรุป:** เลขที่ใบสมัคร, วันเวลา, ชื่อทีมสองภาษา, สมาชิก (รหัส ชื่อ เบอร์), ที่ปรึกษา, **PIN** + คำเตือนให้เก็บเป็นความลับ, สถานะ "รอ admin ตรวจสอบ". iPhone/Safari อาจบล็อกดาวน์โหลดอัตโนมัติ → หน้าสำเร็จต้องมีปุ่ม "บันทึกภาพอีกครั้ง"

## 6. หน้าตรวจสอบการสมัคร
| ส่วน | รายละเอียด |
|---|---|
| ฟอร์มค้นหา | ชื่อทีมอังกฤษ + PIN + ปุ่มตรวจสอบ · ไม่พบ/PIN ผิด แสดงข้อความเดียวกัน |
| สถานะ | `pending` = **รอ admin ตรวจสอบ** (เหลือง) → `approved` = **การสมัครสำเร็จ** (เขียว) + เลขที่ใบสมัคร/วันที่ |
| สรุป | ชื่อทีม สมาชิก ที่ปรึกษา — อ่านอย่างเดียว (แก้ข้อมูลผ่านการติดต่อกรรมการ/admin) |
| ช่องอัปโหลด | เฉพาะช่องที่ admin เปิด: ชื่อ คำอธิบาย ชนิดไฟล์ ขนาดสูงสุด กำหนดส่ง · ส่งทับได้จนถึงกำหนด · แสดงสถานะไฟล์ที่ส่งแล้ว |
| ติดต่อกรรมการ | แผงช่องทางติดต่อ (admin แก้ได้) + กล่องส่งข้อความทางเดียว *(ข้อเสนอ)* |

## 7. ส่วน Admin (`#/admin`, Supabase Auth + **MFA บังคับ**, บัญชีสร้างเองใน Supabase เท่านั้น)
| แท็บ | ทำอะไรได้ |
|---|---|
| ภาพรวม | จำนวนทีม ทีมรอตรวจ/สำเร็จ สถานะรับสมัคร เวลาสำรองล่าสุด |
| ปี/รอบการจัด | รายการรอบ · สร้างปีใหม่ (คัดลอกข้อความ+ช่องส่งไฟล์แบบปิด) · ตั้งเป็นปีปัจจุบัน · โหมดรับสมัคร (ตามช่วงเวลา/เปิดบังคับ/ปิดบังคับ) + วัน-เวลาเปิด-ปิด · กำหนดการสำคัญ · จำนวนสมาชิกสูงสุด |
| เนื้อหาหน้าเว็บ | ทั้งเว็บ: โลโก้ ชื่อเว็บ footer ติดต่อ ป้ายปุ่ม · เฉพาะปี: ชื่อโครงการ รายละเอียดย่อ พื้นหลัง PDF ข้อความรับทราบ/PDPA |
| รายชื่อทีม | ตาราง ค้นหา กรองสถานะ ดูรายละเอียด เปลี่ยนสถานะ แก้แทนทีม ลบทีม รีเซ็ต PIN ส่งออก CSV (UTF-8 BOM) |
| ช่องส่งไฟล์ | สร้าง/แก้/เปิด-ปิดช่อง ดู/ดาวน์โหลดไฟล์ที่ทีมส่ง |
| ภาพกิจกรรม | สร้างอัลบั้ม อัปโหลดหลายไฟล์ (ย่อในเบราว์เซอร์) ลิงก์อัลบั้มภายนอก เผยแพร่/ซ่อน จัดเรียง |
| สำรอง/รีเซ็ต | ส่งออก ZIP · รีเซ็ตข้อมูลผู้เข้าร่วมของรอบ (หัวข้อ 14) |

หน้าตรวจสอบของผู้สมัครอ่านอย่างเดียว; ทุกการเปลี่ยนแปลงของ admin บันทึกลง `audit_log`

## 8. โมเดลข้อมูล
ดูโครงสร้างจริงที่ `SCHEMA` ใน `gas/Db.gs` (เดิมเป็น Postgres: `supabase/schema.sql` ในประวัติ git) — ตาราง: `admins`, `site_settings` (ค่าทั้งเว็บ), **`editions`** (ค่าเฉพาะรอบ), `teams`, `members`, `advisors`, `consents`, `upload_slots`, `uploads`, `messages`, **`gallery_albums`**, **`gallery_photos`**, **`backup_log`**, `audit_log`, `lookup_attempts`, `rate_limits`
- `editions`: year, title, subtitle, intro_text, background_path, rules_pdf_path, ack_text, pdpa_text, key_dates (jsonb), max_members (1–20, ค่าเริ่ม 7), reg_mode (auto/open/closed, ค่าเริ่ม closed), registration_opens_at/closes_at, ref_prefix, ref_counter, is_current (partial unique: ได้รอบเดียว), status (draft/active/archived), last_backup_at, purged_at, purge_mode
- `teams.edition_id`, `members.edition_id` (FK คู่ไปยัง teams) → unique `(edition_id, student_id)` และ `(edition_id, name_en_key)`
RPC สาธารณะ: `public_site`, `student_id_taken`, `submit_team`, `lookup_team`, `confirm_upload`, `send_message` · RPC admin: `admin_reset_pin`, `admin_create_edition`, `admin_set_current_edition`, `admin_mark_backup` · ภายใน (service_role): `_prepare_upload`, `_purge_edition`, `_edition_file_paths` · ตัวช่วย: `_verify_team`, `_rate_limit`, `_registration_open`, `_edition_public`, `is_admin` — ตรรกะเดิมใน Postgres ปัจจุบันอยู่ใน `gas/*.gs`
คีย์ `site_settings` (ทั้งเว็บ): site_name, logo_path, details_button_label, apply_button_label, submit_label, footer_text, contact_info, gallery_intro

## 9. ความปลอดภัยและ PDPA
| ความเสี่ยง | มาตรการ |
|---|---|
| เดา PIN (มีแค่ 10,000 แบบ) | จำกัด 5 ครั้ง/ชื่อทีม/15 นาที แล้วล็อกชั่วคราว (`lookup_attempts`, นับแม้ไม่มีทีมนั้น) · ข้อความเดียวกันทั้งไม่พบ/ผิด |
| อ่านรายชื่อนักศึกษาตรงๆ | RLS: anon อ่านได้เฉพาะ `site_settings` (public) และ `upload_slots` ที่เปิด; ข้อมูลทีมผ่าน RPC เท่านั้น |
| สุ่มรหัสนักศึกษาดูว่าใครสมัคร | `student_id_taken` คืนแค่ true/false + จำกัดอัตราต่อ IP |
| PIN รั่วจาก DB | เก็บเป็น bcrypt hash, admin เห็น PIN ไม่ได้ ทำได้แค่รีเซ็ต |
| ไฟล์ทีมถูกดึง | bucket private, signed URL อายุสั้น, ตรวจชนิด/ขนาดตามช่อง |
| บัญชี admin ถูกแฮก | รหัสผ่านยาว + 2FA + เขียนได้เฉพาะ role admin (`public.admins`) |
| ลบ/รีเซ็ตข้อมูลผิดพลาดหรือโดยผู้ไม่มีสิทธิ์ | ผ่าน Edge Function `admin-purge` เท่านั้น: admin + aal2 + พิมพ์ `PURGE <ปี>` + สำรองภายใน 24 ชม. (ตรวจซ้ำใน SQL) + audit_log |
| ไฟล์สำรองรั่ว | สร้างในเครื่อง admin ไม่ส่งไป GitHub/เซิร์ฟเวอร์อื่น เก็บแบบจำกัดสิทธิ์ ลบตามนโยบาย |
| อัลบั้มที่ยังไม่เผยแพร่ถูกเห็น | RLS: anon เห็นเฉพาะอัลบั้มที่เผยแพร่ของรอบที่ไม่ใช่ draft |

**PDPA:** ช่องยินยอมต้องระบุวัตถุประสงค์ (ใช้พิจารณาคัดเลือกและติดต่อในการประกวดนี้เท่านั้น) ระยะเวลาเก็บ ช่องทางถอนความยินยอม ชื่อผู้ควบคุมข้อมูล — **ต้องให้ฝ่ายกฎหมาย/DPO มหาวิทยาลัยตรวจก่อนใช้จริง** เก็บเฉพาะฟิลด์ที่จำเป็น และลบข้อมูล/ไฟล์หลังจบโครงการตามกำหนด `consents` เก็บเวอร์ชันข้อความ (md5) ที่ทีมยินยอมและเวลา

## 10. แผนพัฒนา
ลำดับ: (1) ภาพจำลองให้ผู้จัดยืนยัน ✔ (รวมหลายปี/ภาพกิจกรรม/สำรอง-รีเซ็ต) → ดูขั้นย่อยใน `docs/PROMPTS.md` (Stage 4b–4d) → (2) ตั้ง Supabase (SQL, bucket, admin) → (3) หน้าหลัก + แท็บแก้เนื้อหา + PDF → (4) หน้าสมัคร → (5) หน้าตรวจสอบ + อัปโหลด → (6) Admin ส่วนที่เหลือ + CSV → (7) ทดสอบ: Confirm พร้อมกันด้วยรหัสซ้ำ, ล็อก PIN, ดาวน์โหลดใบสรุปบน iPhone/Android, จอเล็ก, ข้อความ PDPA
ต้องมีก่อนเริ่ม: บัญชี GitHub, โปรเจกต์ Supabase (region Singapore), อีเมล admin, ไฟล์โลโก้/พื้นหลัง/PDF, ข้อความ PDPA ที่อนุมัติ

## 12. รอบการจัดงานหลายปี (Editions)
ทีม สมาชิก ที่ปรึกษา ไฟล์ ความยินยอม ข้อความ ช่องส่งไฟล์ และข้อความ/PDF/พื้นหลัง/กำหนดการของแต่ละปี ผูกกับ `editions`; โลโก้ ชื่อเว็บ footer ติดต่อ ป้ายปุ่ม อยู่ที่ `site_settings`; ภาพกิจกรรมถาวร
- มีรอบ `is_current` ได้รอบเดียว; รอบใหม่เริ่มเป็น draft + ปิดรับสมัคร; ตั้งเป็นปีปัจจุบันแล้วหน้าหลัก/ฟอร์มเปลี่ยนทันที
- รหัสนักศึกษาซ้ำตรวจ **ภายในรอบเดียวกัน** (นักศึกษาเดิมสมัครปีใหม่ได้) · เลขใบสมัครมีรหัสปี เช่น ST26-0001
- ขั้นตอนขึ้นปีใหม่: สำรอง → รีเซ็ตปีเก่า → สร้างปีใหม่ (คัดลอก) → ตั้งช่วงรับสมัคร/กำหนดการ/PDF → ตั้งเป็นปีปัจจุบัน

## 13. ช่วงเวลารับสมัคร และ หน้าภาพกิจกรรม
**ช่วงเวลา:** `reg_mode` = `auto` (เปิดเมื่อถึง opens_at ปิดเมื่อถึง closes_at; ไม่มี opens_at = ปิด) | `open` (บังคับเปิด) | `closed` (บังคับปิด) และรอบต้อง `status = active` เซิร์ฟเวอร์ตัดสินด้วยนาฬิกาตัวเองใน `_registration_open`; `submit_team` ตอบ `registration_closed` ถ้าหมดเวลาขณะกรอก
**ภาพกิจกรรม `#/gallery`:** แท็บปี → การ์ดอัลบั้ม → กริดภาพ → lightbox (ก่อนหน้า/ถัดไป/ปิด/Esc/ลูกศร) · อัลบั้มอาจเป็นลิงก์ภายนอก (https) · admin อัปโหลดหลายไฟล์ ย่อในเบราว์เซอร์ (ด้านยาว ≤ 2000 px + ภาพย่อ 480 px) เก็บใน bucket `gallery` (public) · เผยแพร่/ซ่อนต่ออัลบั้ม · ไม่ถูกลบเมื่อรีเซ็ตข้อมูลผู้เข้าร่วม

## 14. สำรองและรีเซ็ตข้อมูลผู้เข้าร่วม
**สำรอง:** ปุ่มสร้าง ZIP ในเบราว์เซอร์ (teams/members/advisors/consents/messages/uploads เป็น CSV UTF-8 BOM + `data.json` + ไฟล์ที่ทีมส่งใน `files/`) แล้วเรียก `admin_mark_backup` บันทึก `last_backup_at` + `backup_log` — ไม่รวมภาพกิจกรรม และไม่ส่งไฟล์ไปที่ใดอัตโนมัติ (repo/Pages เป็นสาธารณะ จึงไม่ตั้ง dump อัตโนมัติไปไว้บน GitHub) นอกจากนี้ Supabase มีการสำรองระดับแพลตฟอร์มตามแพ็กเกจ (ตรวจในหน้า Supabase)
**รีเซ็ต** (Edge Function `admin-purge`, JWT verification เปิด):
| โหมด | ผล |
|---|---|
| `anonymize` (แนะนำ) | เก็บชื่อทีม ref_no สถานะ `members_count_at_purge`; ลบรหัสนักศึกษา ชื่อ เบอร์ ที่ปรึกษา ความยินยอม ข้อความ ไฟล์ที่ทีมส่ง; ทำให้ PIN ใช้ไม่ได้ |
| `delete` | ลบทีมและข้อมูล/ไฟล์ทั้งหมดของรอบนั้น |
ต้องผ่านทุกข้อ (ตรวจฝั่งเซิร์ฟเวอร์): เป็น admin · JWT `aal2` (MFA) · confirm = `PURGE <ปี>` · มีสำรองภายใน 24 ชม. (ตรวจซ้ำใน SQL `_purge_edition`) · ลบแถวในฐานข้อมูลก่อน แล้วลบไฟล์ผ่าน Storage API (รายงานไฟล์ที่ลบไม่ได้) · บันทึก `audit_log` · ไม่แตะ: ภาพกิจกรรม ข้อความ/ตั้งค่าของรอบ นิยามช่องส่งไฟล์ รอบอื่น
ยังไม่ได้ทดสอบ: Edge Functions บน Supabase จริง, ฝั่งหน้าเว็บ, Confirm พร้อมกัน, การลงทะเบียน MFA

## Changes made while preparing the hand-off (differ from the Docs version)
1. **Uploads:** an RPC cannot create Storage signed URLs, so the doc's `request_upload` became an **Edge Function** `request-upload` (calls private SQL `_prepare_upload`) plus RPC `confirm_upload` that records the file after the browser uploads it.
2. **PIN hashing:** bcrypt (`crypt(pin, gen_salt('bf'))`) instead of a separate per-team salt column — same intent, simpler.
3. **Phone rule:** SQL enforces 10 digits starting with 0 (the mockup was looser: 9–10 digits). The app must follow the SQL.
4. **order_no CHECK** is 1–20 in SQL; the real cap is `editions.max_members` (default 7), enforced in `submit_team`.
5. **Mockup limits:** `design-reference/` uses sample data (e.g. Sample Team / PIN 4821) and placeholder logo "ST"; the project description and footer text are placeholders.

6. **v2 (multi-year):** added editions, registration window, gallery, backup/reset, `admin-purge`, `public_site()`; the sections 12–15 above are new. Max team size is 7.
